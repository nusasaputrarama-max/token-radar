## Executive assessment

The radar-4 remediation materially improved input validation, valuation disclosure, board coverage checks, deterministic ordering, and category-based farm-plan generation. The output-path guard added on 17 November is now on `main`; PR #2 is merged.

The implementation is **not ready for a clean audit closure**. The largest remaining issue is the same unresolved P1 from the prior review: the 7-day growth and listing-age multipliers remain uncalibrated, and no growth-removal rank-sensitivity test exists. More importantly, the farm-plan generator still turns broad category labels into concrete financial actions and rewards claims that the snapshot cannot substantiate. Its current language conflicts with the handoff requirement not to fabricate protocol capabilities, supported assets, rewards pages, or points programmes.

## Findings

### P1-01 — Farm plans still assert protocol capabilities and reward programmes without evidence

**Evidence:** `lib/model.ts`, `actionFor()`, `weeklyFor()`, `claimFor()`, approximately lines 528–640.

The generator selects concrete actions from a broad DefiLlama category, but the snapshot schema contains only category, chains, TVL, growth, market-cap metadata, and listing date. It does not establish supported assets, pool availability, vault availability, staking assets, destination apps, reward pages, points programmes, cashback, or protocol-specific eligibility.

Examples in the current source include:
- Lending rows are told to supply USDC; DEX rows to provide liquidity to a “main pool”; curator rows to deposit into a vault; RWA rows to mint a yield-bearing asset; and governance rows to deposit funds.
- The weekly step tells users to borrow, bridge, restake, mint/redeem, rebalance, vote, or spend, depending only on category.
- `claimFor()` asserts the existence of protocol-owned points/rewards pages across almost every family, including chains, indexes, insurance, payments, and CeDeFi. The source snapshot contains no evidence that these programmes or pages exist.

The phrase “verify on the official app” does not cure an instruction that first presents an unsupported asset/action as the expected route. The current family-level test only checks that a generic fallback is avoided; it does not verify that a family action is supported by a particular protocol.

**Required remediation:** Until there is protocol-level source evidence, make the default action verify-first and non-transactional. Represent capabilities as evidence-backed fields (source URL, observed date, supported asset/action, confidence) before emitting a deposit, bridge, mint, borrow, trade, rewards, or points instruction. Do not generate a claim/rewards page instruction unless the page/programme is explicitly verified. Add negative tests proving missing evidence never produces a financial action or rewards claim. Muse must not invent the missing evidence.

**Status:** OPEN — implementation and tests required.

### P1-02 — Growth and maturity calibration remains unresolved; ranking sensitivity is untested

**Evidence:** `lib/model.ts` model constants and `impliedValue()`; `tests/model.test.mjs`; `docs/MUSE_REMEDIATION_REPORT.md` unresolved finding 1.

The model still applies the capped 7-day TVL change with asymmetric weights (`growth_up: 0.5`, `growth_down: 0.7`) and a one-way listing-age multiplier from 0.70 to 1.00 over 1,460 days. The prior report explicitly records that no growth-removal rank-sensitivity test was added. The existing sealed-snapshot test pins constants to the radar-3 values; it does not measure how rankings change when growth or maturity effects are removed or perturbed.

This is not fixed by disclosing the factors in the UI. The output remains sensitive to one short TVL window and an uncalibrated listing-age hypothesis. The sealed snapshot has only `change_7d`, so a 30/90-day trend cannot be inferred from the current input.

**Required remediation:** Add a deterministic sensitivity analysis that compares the current ranking with (a) growth multiplier neutralized to 1.0, (b) maturity multiplier neutralized to 1.0, and (c) both neutralized. Report rank movement (median, p90, max, and top-N membership changes) using the exact sealed snapshot. Keep the submitted model unchanged unless Rama explicitly authorizes a new model version/submission; treat sensitivity output as diagnostic, not a silent recalibration. If the sealed snapshot is unavailable, implement synthetic fixture tests and mark the real-board sensitivity as blocked.

**Status:** OPEN — prior P1 remains partially addressed.

### P2-01 — Family classifier has an overlapping rule that misclassifies yield aggregators

**Evidence:** `lib/model.ts`, `familyFor()`, approximately lines 551–568; `tests/model.test.mjs`, family fixtures.

The DEX rule checks `c.includes('yield')` before the curator rule checks `c.includes('aggregator')`. Therefore a category such as `Yield Aggregator` is classified as `dex`, not `curator`. That routes the protocol into a main-pool liquidity action and weekly swap/fee collection, rather than the curator/vault branch. The fixture list includes `Yield Aggregator`, but its assertion only verifies that the entry action is not the old generic deposit fallback; it never asserts the expected family or expected action.

There is a related normalization mismatch: `normCategory()` trims and lowercases categories for comparable grouping, but `familyFor()` only lowercases. Leading/trailing whitespace can therefore change farm-family classification even when the category is otherwise valid.

**Required remediation:** Normalize family labels consistently before matching. Make overlapping categories explicit and order the more specific rules before broad substrings (or use an explicit category-to-family map). Change fixtures to assert `familyFor()` results and representative action/weekly/claim behavior for every category, including `Yield Aggregator`, whitespace variants, and case variants.

**Status:** OPEN — deterministic classification defect with inadequate test assertions.

### P2-02 — Output-path symlink protection is check-then-use, not atomic

**Evidence:** `lib/output-path.ts` and `main.ts` around output validation and recursive cleanup.

The output path is checked before directory creation and checked again immediately after `mkdirSync()`. Recursive deletion then occurs in a later sequence of path-based `rmSync(join(out, name), ...)` calls. A concurrent process able to modify a writable ancestor could replace a checked path component with a symlink between the final validation and cleanup. The current tests cover a symlink already present at validation time; they do not exercise a path swap between validation and deletion.

This is a local race requiring write access to a relevant parent directory; it is not evidence of a remotely exploitable vulnerability. The guard meaningfully blocks static unsafe paths, but the current implementation should not be described as eliminating all symlink-redirection races.

**Required remediation:** Prefer a private, newly created output directory under a parent not writable by untrusted processes, and fail closed if ownership/permissions do not satisfy that assumption. Document the threat model. Add an adversarial race test if the chosen design claims to defend against concurrent path replacement. Avoid overstating guarantees that path-based checks cannot provide atomically.

**Status:** OPEN — residual local race / threat-model gap.

### P2-03 — Chain deduplication is exact-string only, so cosmetic variants can inflate breadth

**Evidence:** `lib/model.ts`, `parseSnapshot()` chain normalization.

The parser filters blank chain strings and applies `new Set()`, but retains the original strings and compares them case-sensitively. Values such as `Ethereum`, `ethereum`, and ` Ethereum ` can survive as separate entries and inflate the breadth multiplier, even though they refer to the same chain. This contradicts the intended invariant that duplicate chain labels cannot inflate breadth.

**Required remediation:** Normalize a comparison key (trim + case-fold) before deduplication while preserving one canonical display label. Add tests for whitespace and case variants, not only exact duplicates.

**Status:** OPEN — input-normalization gap; impact depends on whether such variants occur in the sealed snapshot.
